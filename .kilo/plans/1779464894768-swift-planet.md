## ANÁLISE ATUAL (BASELINE)

### Estado do Backend (fato)

```
Routes → Drizzle ORM diretamente
         ↓
   server/src/db/index.ts  (singleton drizzle+postgres)
         ↓
   PostgreSQL (TCP direto, sem pooler)
```

- **Nenhum Repository pattern existe** — todas as 38 rotas chamam `db.select()/insert()/update()/delete()` diretamente sobre o drizzle
- `server/src/db/index.ts` exporta um `db` singleton `drizzle(client, { schema })` — ponto de injeção único
- Config em `server/src/config.ts` (Zod-validated): `DATABASE_URL`, `JWT_SECRET`, `CORS_ORIGINS`, `NODE_ENV`, etc.
- `server/src/lib/health.ts` faz `db.execute(sql\`SELECT 1\`)` diretamente — não conhece provider
- Serviços existentes: `auditLogService`, `coverageCityService`, `sse`, `rateLimitStore` (in-memory + Redis), `printing/service`+`drivers`, `opening-status`, `brazilian-holidays`, `cleanupAuthSessions`
- 60+ tabelas em 10 módulos de schema (core/ customer/ merchant/ commerce/ saas/ ops/ operations/)

### Estado do Frontend (fato)

```
App → hooks → repositories → api modules → httpClient → fetch
```

- 136 matches de useQuery/useMutation, centralizados em `src/api/queryKeys.ts`
- httpClient: JWT auto-refresh (401 → /auth/refresh → retry 1×), exponential backoff (3 retries), dedupe GET por path via `inFlight Map`
- MSW 2+msw/browser +msw/node: 57+ handlers em 10 arquivos, 7 cenários (default, empty_store, kitchen_congested, payment_declined, courier_offline, tenant_expired, merchant_blocked)
- Fixtures: 31 arquivos em `src/mocks/fixtures/` (tipados via `/dto`)
- Cenário swapruntime via `window.__MSW_SCENARIO`

### Lacunas

| Problema | Impacto |
|---|---|
| 0 camada de abstração backend | Impossível trocar PostgreSQL por memória sem reescrever rotas |
| Testes de backend usam PostgreSQL | Lentos, frágeis, requerem infraestrutura |
| Handlers MSW não reutilizam repositórios reais | Drift inevitável entre mock e API |
| Zero snapshots de sistema | Ambiente não reproduzível |
| Sem recording/replay | Cenários reais não podem ser reproduzidos |
| Sem offline persistence | App não opera offline |
| Chaos testing inexistente | Resiliência não validada |
| `NODE_ENV === 'test'` seta `DATABASE_URL` fake | Testes ainda dependem de conexão PostgreSQL |

### Provider Selection (Gateway único)

```ts
// server/src/db/provider.ts  — NÚNCA CHAMADO DIRETAMENTE NAS ROTAS
export type DbProvider = 'postgres' | 'memory';

export function resolveDbProvider(env: EnvConfig): DbProvider {
  if (env.DATABASE_PROVIDER) return env.DATABASE_PROVIDER;
  if (env.NODE_ENV === 'test') return 'memory';
  return 'postgres';   // default de produção: sempre PostgreSQL
}
```

### FASE 14 — BACKEND MOCKABLE

**Critério**: backend sobe e responde SEM PostgreSQL, apenas com `DATABASE_PROVIDER=memory`.

**Arquivos criados**:

| Arquivo | Descrição |
|---|---|
| `server/src/ports/repository.ts` | `RepositoryPort<T, Filter, CreateDto, UpdateDto>` — interface única |
| `server/src/ports/index.ts` | Barrel export |
| `server/src/db/provider.ts` | `resolveDbProvider()`, `DbProvider`, `RuntimeCapabilities` |
| `server/src/db/repositories/base-postgres.ts` | `PostgresRepository<T>` — thin wrapper drizzle |
| `server/src/db/repositories/index.ts` | Barrel export |

**Arquivos modificados**:

| Arquivo | Mudança |
|---|---|
| `server/src/config.ts` | Adicionar `DATABASE_PROVIDER` ao envSchema |
| `server/src/db/index.ts` | `createDatabase(env): { db, registry }`  — fábrica, não singleton |
| `server/src/index.ts` | Consumir fábrica, injetar `registry` nas rotas |

**Decisões**:
- `RepositoryPort` é interface genérica única — não há `IXxxxRepository` por tipo, haverá uma implementação genérica por `RepositoryKey` discriminado em Registry.
- `PostgresRepository` é **thin wrapper** — não questiona, não cacheia, delega diretamente ao drizzle. Métricas e log ficam no middleware.
- `HealthCheck` recebe `RepositoryPort` via port de `HealthPort` — não sabe se é postgres ou memória.
- Rota não muda — troca `db.select()` por `reposRestaurant.findMany()` via Registry. Mesma API em ambos os providers.

**Risco**: rotas com joins Drizzle complexos (`with(...)`, relações) precisam de tradução explícita para Filter. Solução: adicionar método `findManyWith(filter, { relations })` à interface.

### FASE 15 — MEMORY REPOSITORIES (A mais complexa)

**Critério**: `DATABASE_PROVIDER=memory` executa todas as 38 rotas sem PostgreSQL. Testes reproduzíveis.

**Arquivos criados**:

| Arquivo | Descrição |
|---|---|
| `server/src/db/repositories/base-memory.ts` | `BaseMemoryRepository<Id, Entity, Filter>` |
| `server/src/db/repositories/memory-tenant-tables.ts` | `TenantIsolatedStorage<Id>` — storage índice por tenantId |
| `server/src/db/repositories/memory-filters.ts` | Filtros equivalentes a Drizzle: `eq`, `ne`, `inArray`, `and`/`or`, `gt`, `gte`, `lt`, `lte`, `isNull`, `isNotNull`, `like`, `ilike` |
| `server/src/db/repositories/memory-transaction.ts` | `MemoryTransactionAdapter` — aco, rollback isolado |
| `server/src/db/repositories/memory-provider.ts` | Instância todas as entidades com memória |
| `shared/services/seed.ts` | Fixture seed service — JSONs por módulo, versionados |

**Contratos determinísticos garantidos**:

```
─ IDs: UUIDv7 determinísticos (seed-based, gerados na inicialização)
─ Timestamps: FixedClock injetado — não usa new Date() diretamente
─ Ordering: ordenação por created_at asc como linha de base
─ Seeds: carregados de JSONs versionados em shared/services/seed/
─ Reset: BaseMemoryRepository.reset() limpa tenant específico, mantendo shared
─ Snapshot: snapshot() / restore(snapshot) serializáveis JSON
```

**Decisões**:
- Single data path storage: `Map<tenantId, Map<id, Entity>>` — isolamento absoluto entre tenants.
- `BaseMemoryRepository` é abstrata; geradores de dados (`SeedGenerationStrategy`) são construturais por módulo, não compartilham referências.
- IDs determinísticos por entidade: cada entidade cria seus IDs na inicialização, `reset` usa novo gerador — delays na criação dos IDs.

### FASE 18 — SNAPSHOT FIXTURES

**Critério**: snapshot de todo o estado do sistema pode ser gravado e restaurado em < 100ms, exatamente igual ao ponto de gravação.

**Arquivos criados**:

| Arquivo | Descrição |
|---|---|
| `shared/snapshot/types.ts` | `SnapshotId`, `SnapshotMeta` (tenantId, timestamp, seed), `SnapshotPayload` |
| `shared/snapshot/serializer.ts` | `serialize(snapshot)`, `deserialize(buffer)` — JSON canônico |
| `shared/snapshot/registry.ts` | `SnapshotRegistry` — cria, lista, deleta, busca por tenant/seed |
| `shared/snapshot/fixture-loader.ts` | `loadFixture(name)`, `loadTenantFixtures(tenantId)` |
| `shared/snapshot/snapshot-manager.ts` | Orquestrador que orquestra todos os módulos snapshot |

**Arquivos modificados**:
- `shared/services/seed.ts` — seeds carregados de snapshots quando disponível
- `server/src/db/repositories/base-memory.ts` — ganha `snapshot()` / `restore(snapshot)` por tenant
- `BaseMemoryRepository.snapshot()` retorna JSON canônico: `{ seed, fixedClockTime, allTables: { table: [rows...] } }`

**Decisões**:
- Snapshots são **tenant-scope** — um snapshot NÃO cruza tenants.
- Snapshots são **versionados por seed** — mesmo seed + mesmos módulos de seed = mesmo snapshot.
- Registry armazena metadados; dados comprimidos como JSON canônico (sem whitespace aleatório).
- `SnapshotVersion` é schema Evolution-aware — versões são declaradas por módulo (`snapshotVersions: { users: 'v1', orders: 'v1', … }`).

**Cenários compostos** disponíveis:

| Cenário | Ação Injectada | Verificação |
|---|---|---|
| `high_demand` | Seed 100+ orders em 10min | Latência < 3s, não 500 |
| `kitchen_congested` | 80+ preparing, tempo médio > 30min | Return 202, SSE streaming |
| `courier_offline` | ZERO deliverers disponíveis na região | Return 503 {code: NO_COURIERS} |

- Seeding por módulo, não por seed global — módulos rejeitam dados com versão de seed desconhecida.
- `fixedClock` compartilhado entre frontend build-time (injetado via `VITE_SCENARIO_SEED`) e backend.
- Frontend MSW handlers consultam o mesmo `ScenarioOrchestrator` do backend via shared library `shared/scenarios/`.

**Arquivos criados**:

| Arquivo | Descrição |
|---|---|
| `shared/replay/types.ts` | `CassetteId`, `CassetteEntry`, `Cassette` (array de entries) |
| `shared/replay/recorder.ts` | `ReplayRecorder` — grava request+response enquanto o sistema roda |
| `shared/replay/player.ts` | `ReplayPlayer` — lê cassette e reprodut por ordem |
| `shared/replay/sanitizer.ts` | Remove/sanitiza tokens, PII, IPs de cassettes |
| `shared/replay/cassette-store.ts` | `CassetteStore` — armazena cassettes em filesystem JSON |
| `shared/replay/replay-middleware.ts` | Middleware Hono que intercepta req/res e salva em replay store |
| `shared/replay/versioned-replay.ts` | Cassettes versionados por schema — rejeita cassettes com schema incompatível |

**Sanitização**:

```
headlers: sanitizeHeader  → [
  'authorization':  'Bearer <SANITIZED>'
  'set-cookie':     '<SANITIZED>'
]
body:   sanitizeBody   → {
  'password':       '<SANITIZED>'
  'cpf':            '<SANITIZED>'
  'email':          '<SANITIZED>'
  'token':          '<SANITIZED>'
  // Não altera campos não-PII
}
status/timing preservados
```

**Cassette versionamento**:
- `CassetteHeader`: `{ version: '1.0', recordedAt: timestamp, schemaVersion: string, providedBy: 'postgres' | 'memory', seed: string }`
- Runtime compara `schemaVersion` do cassette com `currentSchemaVersion` do repositório — rejeita com erro explícito se divergentes.
